# LDPC Decoder OMS Algorithm Document Project

LDPCデコーダ（Offset Min-Sum アルゴリズム）の理解と、
新規参加者への技術継承を目的としたドキュメントプロジェクトです。

## 📖 プロジェクトの目的
*   **技術の明文化**: Offset Min-Sum (OMS) アルゴリズムの詳細と
    ハードウェア実装への落とし込みを体系化する。
*   **教育資産の構築**: 符号理論の基礎知識がない回路設計者が、
    スムーズに設計・実装に参加できるようにする。
*   **ASIC実装への最適化**: RTL設計における量子化、並列度、
    スループット等の検討事項を整理する。

## 👥 推進体制
本プロジェクトは、人間とAIのハイブリッドチームで進めます。

| 役割 | 名前 | 担当内容 |
| :--- | :--- | :--- |
| **人間（承認者）** | **沖田** | 最終承認、プロジェクトの方向性決定、図解作成 |
| **AI（主案作成）** | **古代** | ドキュメントの執筆（第一稿の作成）、構成案の提示 |
| **AI（レビュー）** | **真田** | 技術的観点からのレビュー、実装上の課題指摘 |

## 🎯 想定読者
本ドキュメントの想定読者は、以下のスキルセットを持つエンジニアです。

*   **前提知識あり**: デジタル回路設計・RTL設計の基礎知識
*   **前提知識なし**: 通信理論・符号理論

符号理論の「暗黙知」（例: 論文中の `+` 記号が算術和ではなく
GF(2)上のXORを意味する等）につまずかないよう、
必要な基礎理論は本ドキュメント内で解説します。

## 📐 ドキュメント作成の指針
本ドキュメントの執筆・図解・レビューにあたり、以下の方針を徹底します。

### 1. 表記法はデファクトスタンダードに従う
*   **用語・変数**: 基準文献（Chen 2005）の記法に統一する。
    定義は `docs/01_intro/index.adoc` を参照。
*   **数式**: LaTeX記法（`stem:[...]`）を使用し、
    Chen (2005) の式表現に準拠する。
*   **図のノード表記**:
    *   変数ノード (VN): **円 (○)**
    *   チェックノード (CN): **四角 (□)**
    *   エッジ: **無方向線**
    （内川論文・Wikipedia "Belief propagation" 等の
    主要文献のデファクトスタンダードに準拠）

### 2. 具体例を用いて説明する
*   抽象的な説明には必ず具体例を添える。
*   本ドキュメント全体で使用する**標準具体例**として、
    以下の 3×6 検査行列を一貫して使用する:
```Text
    ┌             ┐
    │ 1 1 0 1 0 0 │  (CN1)
H = │ 0 1 1 0 1 0 │  (CN2)
    │ 1 0 1 0 0 1 │  (CN3)
    └             ┘
```
*   n=1,2,3: 情報ビット（VN次数=2）
    *   n=4,5,6: パリティビット（VN次数=1）
    *   CN次数: 全て3（Min1/Min2の説明に最適）

### 3. 参考文献の表記法
参考文献は IEEE 形式で記述する。
```Text
[著者], "[タイトル]," [雑誌名], vol. XX, no. XX, pp. XXX-XXX, Mon. YYYY.
```

主要参考文献:
*   内川 浩典, "低密度パリティ検査符号 (LDPC 符号)
    ―Robert G. Gallager 先生の 2020 年日本国際賞受賞に寄せて,"
    電子情報通信学会 基礎・境界ソサイエティ Fundamentals Review,
    vol. 14, no. 3, pp. 217-228, 2021.
*   J. Chen, A. Dholakia, E. Eleftheriou, M. P. C. Fossorier,
    and X.-Y. Hu, "Reduced-complexity decoding of LDPC codes,"
    IEEE Trans. Commun., vol. 53, no. 8, pp. 1288-1299, Aug. 2005.

### 4. 暗黙知を明示する
符号理論の文脈で自明とされる事項も、
RTL設計者にとっては初見となる可能性がある。
「当然のこと」と判断せず、必要な前提知識は
本文中で明示的に解説する。

## 🛠 ツールと形式
*   **ポータル**: README.md（Markdown形式）
*   **ドキュメント本体**: Asciidoc (`docs/*.adoc`)
*   **数式**: LaTeX 形式 (`stem` を使用)
*   **図表**:
    *   **draw.io**: `.drawio` ファイルを正本として管理。
    *   **画像形式**: `.svg` または `.png`（Git管理対象）。
    *   **その他**: PlantUML / Mermaid / Python (Matplotlib) も適宜使用。
*   **管理**: Git によるバージョン管理

## 📂 フォルダ構成
*   `docs/`: ドキュメントソース本体。`index.adoc` が親ファイル。
*   `figures/`: 図表、グラフ生成スクリプト
    *   `drawio/`: draw.io ソースファイル（Git管理対象）
    *   `images/`: エクスポートされた画像ファイル（Git管理対象）
    *   `scripts/`: ドキュメント掲載用のグラフ生成専用。
*   `references/`: 参考文献リスト。URLやBibTeX情報を管理。

## ⚙️ 環境構築
ドキュメントのビルド（HTML/PDF出力）には `Asciidoctor` が必要です。
詳細は `docs/00_setup.adoc`（予定）を参照してください。

## 🚀 ワークフロー
1.  **沖田**が draw.io にて標準具体例に基づく図解を作成。
2.  **古代**が各章のドラフト（主案）を執筆し、図解と整合させる。
3.  **真田**が技術的な妥当性と実装の観点からレビュー。
4.  **沖田**が内容を確認し、最終承認・マージを行う。
